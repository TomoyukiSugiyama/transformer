# Phase 5: 生成品質向上 — スケール 4 軸の検証

[Phase 4b](phase4.md) / [Phase D](phase_d.md) で **アーキテクチャ刷新は完了**したが、 生成文の日本語が
局所的にしか正しくないという課題が残った。 観測された主な問題:

- 局所的な単語選択は妥当だが、 文脈と整合しない (「いかさま」 が場違いに出現、 等)
- 1-2 文単位では成立するが 3 文目以降で破綻する
- 助詞・活用の細かな誤り、 未完文の頻発

これらは **アーキテクチャ要因ではなく、 容量・データ・推論手法のスケール律速** と分析。
Phase 5 では 4 軸を **コスト順** に検証する:

## ロードマップ

| 段階 | 項目 | 仮説 | 実装コスト | 学習時間 | 状態 |
|------|------|------|-----------|---------|------|
| 5-1 | **top-p (nucleus) sampling** | top-k=5 の保守性が品質を下げる | 1-2 時間 | なし (推論のみ) | ✅ 完了 |
| 5-2 | **max_len 拡張 (256 → 512)** | 5-10 文しか見えない、 RoPE 真価検証 | 2-3 時間 | x2.5 (再学習) | 🚧 学習準備完了 |
| 5-3 | **コーパス拡大 (1M → 5M+ char)** | データ不足が奇妙な単語混入の主因 | 半日 (スクリプト) | x2 | 未着手 |
| 5-4 | **モデル拡大 (d_model 384 → 512/768)** | 容量不足、 日本語の複雑さ | 1 時間 (Config) | x3-8 | 未着手 |

### 順序の根拠

- **5-1 を最初に**: 既存 [Phase 4b RMS+SwiGLU best.bin](phase_d.md#phase-d-3-swiglu-ffn) でそのまま検証できる。
  「今のモデルで何処まで上がるか」 のベースラインを取る
- **5-2 を次に**: 既存実装 (RoPE 含む) で動く。 max_len 拡張は RoPE の本領発揮場面なので [Phase D-2](phase_d.md#phase-d-2-rope) の追加検証も兼ねる
- **5-3 を 5-4 より前に**: モデル拡大 → コーパス据置 では過学習が悪化する (10.7M params で既に step 700 から overfit)。
  データ拡大が **モデル拡大の前提条件**
- **5-4 を最後に**: 1 step あたり最大 8 倍時間がかかる (M1 Max で `d_model=768 + max_len=512`)。
  データ・サンプリングが整った状態で **容量律速を最終確認**

## Phase 5-1: top-p (nucleus) sampling

### 仮説

現状 `top_k=5, temperature=1.0, repetition_penalty=1.2` は **過度に保守的**:

- top_k=5 は上位 5 候補のみから選択。 モデルが不確かな場面で 「**popular だが文脈に合わない単語**」 を選ぶ
- repetition_penalty 1.2 は強めで、 自然な反復 (「私は…私は…」 のような同主語連続) を抑制する副作用も

top-p (nucleus) sampling は **動的に候補数を変える**:
- モデルが確信を持つ場面では候補が 1-2 個に絞られる (低エントロピー)
- 不確かな場面では候補が広がる (高エントロピー)

これにより 「**自信のある所はビシッと、 不確かな所は緩く**」 という人間的なバランスが出る。

### 実装

`src/output_head.rs` (または `language_model.rs`) に `top_p_sample` を追加:

```rust
pub fn top_p_sample(logits: &[f32], p: f32, temperature: f32) -> usize {
    // 1. logits / temperature でスケール、 softmax で確率化
    // 2. 確率の降順インデックスを取る
    // 3. 累積確率が p を超えるまでの候補を残す
    // 4. 残った候補の中で weighted random sampling
}
```

`LanguageModel::generate_top_p(prompt, max_new, p, temperature, repetition_penalty)` を追加。

### テスト戦略

`src/output_head.rs` の単体テスト:
- `top_p_p_one_includes_all`: `p=1.0` で全候補が残る
- `top_p_p_small_includes_one`: `p=0.1` で 1 候補のみ
- `top_p_threshold_inclusive`: 累積確率が `p` をちょうど超える点で打ち切る
- `top_p_with_temperature`: temperature が確率分布に正しく作用する

### 評価

既存 [Phase 4b RMS+SwiGLU best.bin](phase_d.md#phase-d-3-swiglu-ffn) (val_ppl 18.70) で、 同 prompt に対し以下を比較:

| 設定 | 生成例の質 |
|---|---|
| top_k=5, t=1.0 (現状) | (baseline) |
| top_p=0.9, t=1.0 | |
| top_p=0.95, t=1.0 | |
| top_p=0.9, t=0.8 | (より保守的) |
| top_p=0.9, t=1.2 | (より創造的) |

### 期待値

- 「奇妙な単語混入」 が減る (top-k では機械的に上位 5 を選ぶ問題を解消)
- 自然な文章の長距離一貫性が体感で改善
- val_ppl は **変化しない** (学習指標とは無関係)

### 注意点

- 既存 `generate_top_k` も残す (比較用)
- repetition_penalty は据置 (top-p と独立な機構なので影響なし)

### 実装結果 (✅ 完了)

[Phase 4b RMS+SwiGLU+RoPE best.bin (val_ppl 18.84, step 600)](phase_d.md#phase-d-2-rope) で同じプロンプトに対し top-k=5 と top-p=0.9 (どちらも `temperature=1.0`, `repetition_penalty=1.2`) を比較した。

> RoPE checkpoint は val_ppl で SwiGLU best (18.70) にわずかに劣るが、 サンプリング戦略の比較目的にはどちらも有効。
> Phase 5-2 で max_len 拡張を予定しているため、 そのまま乗り換えやすい RoPE 版を採用した。

#### 並列出力サンプル (6 プロンプトの抜粋)

| prompt | top-k=5 | top-p=0.9 |
|--------|---------|-----------|
| 「私は」 | 「お亡くなりましょう」 「奥さん」 「Ｋ」 → こころ調、 整然 | 「弁解しませんでした」 「迷亭が」 「博物館へ足」 → 吾輩は猫である調、 多様 |
| 「先生は」 | 「どんな人です」 → 三四郎調、 短く平易 | 「自分ほど親しみを証明する事ができなかった」 → こころ調、 内省的 |
| 「ある日」 | 「日露を与えた」 → 吾輩は猫である調、 「向き直りが悪い」 | 「三四郎はまだぼんやりと笑った」 「容易に帰らん」 → 三四郎調 |
| 「吾輩は」 | 「猫の方を見た」 「不合議な顔」 (造語あり) | 「鼻子は真面目に聞くような顔付」 → 鼻子の登場で吾輩らしさ |
| 「それから」 | 「兄さんの態度」 → こころ調、 比較的整然 | 「石鹸を落して手提げ」 → 三四郎/草枕系の混在 |

#### 観察

1. **語彙の多様性**: top-p が **「博物館」 「弁解」 「証明」 「鼻子」 「容易に帰らん」** などの特徴的語彙を引き出す。
   top-k=5 では上位 5 候補に常に高頻度の汎用語 (「は」 「を」 「と」 等) が占め、 表現が均質化する傾向

2. **作品判別の解像度**: 同じ prompt でも top-p では作品の特徴が出やすい (「吾輩は」 で 「鼻子」 「主人」 が登場、
   「ある日」 で 「三四郎」 が登場)。 top-k は **どの作品か曖昧な汎用文** に流れがち

3. **構文の破綻リスク**: top-p の方が文構造の破綻 (「不合議な顔」 「日露もの」 等) が **やや増える**。
   ただし top-k でも 「お亡くなりましょう」 のような誤りはあり、 構文破綻の **主因はサンプリングではなく
   モデル容量律速** であることを再確認

4. **体感品質**: 「面白さ」 では top-p > top-k、 「整然さ」 では top-k > top-p。
   論文 (Holtzman et al. 2019) で報告される 「人間らしい多様性」 のトレードオフが本実装でも再現

#### 結論

- **top-p を採用** (`infer()` のデフォルトに top-k と top-p 両方を出力)
- **本実装での生成品質改善は限定的** ⇒ サンプリング側の最適化は概ね飽和
- 構文の正しさ、 段落単位の一貫性は **モデル容量・コーパス・max_len の制約** が支配的
  → **Phase 5-2 以降のスケール側改善が本丸** であることを確認

#### 副次的成果

- `OutputHead::top_p_candidates` を独立メソッドとして切出し、 サンプリング戦略のテスト容易性を向上
- テスト 7 件追加: `p=1.0` で全件残存、 `p≈0` で top-1 のみ、 累積確率打切り (inclusive)、
  temperature 効果、 浮動小数誤差耐性、 vocab id 重複なし、 sampling の正常動作

## Phase 5-2: max_len 拡張 (256 → 512)

### 仮説

現在 char-level で `max_len=256` だと **5〜10 文しか見渡せない**:
- 平均 25-50 字/文 × 256 = 5-10 文
- 「文章の起こし」 から 「結論」 までを 1 つの window で見られない
- 段落単位の構造が学習できない

512 に拡張すれば 10〜20 文 = **段落単位** の文脈が取れるようになる。 また、
[Phase D-2 RoPE](phase_d.md#phase-d-2-rope) の真価は **max_len 拡張時の汎化** にあるので、
この実験で RoPE vs Sinusoidal の差が顕在化する可能性。

### 設定

`Config::aozora_soseki_works_max512()` を実装済 (`src/main.rs`):

| 項目 | Phase 4b | Phase 5-2 |
|------|---------|-----------|
| `run_name` | `phase4b_aozora_soseki_works_d384_n6_char_rms_swiglu_rope` | `phase5b_aozora_soseki_works_d384_n6_char_rms_swiglu_rope_max512` |
| `max_len` | 256 | **512** |
| `batch_size` | 64 | **32** (メモリ補正) |
| `end_step` | 2000 | **1500** (Phase 4b で 600 がピークだったので余裕を見る) |
| `save_every` | 200 | **100** (best 検出粒度を上げる) |
| その他 | RMS + SwiGLU + RoPE, dropout=0.2, lr 1e-3→1e-4 | 同じ |

per-step 1 token あたりの compute は `attention: O(b·h·seq²·d_head) + FFN: O(b·seq·d²)` で、
`64·6·256² + 64·256·384·1536 ≈ 1.6e9 + 9.6e9 = 11.2e9` →
`32·6·512² + 32·512·384·1536 ≈ 3.2e9 + 9.6e9 = 12.8e9` で **+14% の計算量増**。
ただし step あたり token 数は `max_len × batch_size = 16384` で同じ (Phase 4b と直接比較しやすい)。

### 期待値

- val_ppl: 18.84 → **17.5〜18.0** (文脈長拡大による改善)
- per-step 時間: **+14〜30%** (7700 ms → 9000〜10000 ms 程度)
- 完走時間 (end_step=1500): 1500 × 9.5s ≈ **4 時間**
- RoPE の効果が SwiGLU+Sinusoidal 比でより顕著に出る可能性 (副次実験で検証)

### 副次実験 (オプション)

`Config::aozora_soseki_works_max512_sinusoidal()` を実装済。 これも `phase5b_..._sin_max512` として
独立 run name で並走可能。 RoPE 版が完了した後に同じ手順で実行することで
「**max_len 拡張時の RoPE 効果**」 が直接測定できる。

### 実行方法

`src/main.rs` の `main()` で対応する Config を選んで `cargo run --release`:

```rust
let cfg = Config::aozora_soseki_works_max512();
training_and_inference(&cfg);
```

ログは `logs/phase5b_aozora_soseki_works_d384_n6_char_rms_swiglu_rope_max512.log` に保存される想定。

### 注意点

- **メモリ**: M1 Max (32GB) では batch_size=32 で問題ない見込み。 attention の temp が
  `32 × 6 × 512² × 4B ≈ 200 MB / layer` で 6 層計 1.2 GB、 activation 含めても 5 GB 以内
- **学習の不安定化**: もし lr が大きすぎて発散したら `lr_max=5e-4` に下げる
- **早期収束**: Phase 4b でも step 600 で peak だったので、 step 400〜800 を重点監視

## Phase 5-3: コーパス拡大 (1M → 5M+ char)

### 仮説

漱石 7 作品 = 108 万文字は **「特定文体への過学習」 を促進する規模**:
- 各漢字の登場回数: 高頻度漢字 数千回 / 中頻度 数十回 / 低頻度 数回〜0 回
- 低頻度漢字での予測が不安定 → 「奇妙な単語混入」 の主因

明治-大正の主要作家を追加して 380 万字級 (3.5 倍) を目指す:

| 作家 | 主要作品 | 推定文字数 |
|------|---------|-----------|
| **森鴎外** | 舞姫 / 高瀬舟 / 阿部一族 / 雁 / 山椒大夫 | ~50 万 |
| **芥川龍之介** | 羅生門 / 鼻 / 蜘蛛の糸 / 河童 / 蜜柑 等 | ~100 万 |
| **太宰治** | 走れメロス / 人間失格 / 斜陽 | ~70 万 |
| **宮沢賢治** | 銀河鉄道の夜 / 注文の多い料理店 | ~30 万 |
| **国木田独歩** | 武蔵野 / 牛肉と馬鈴薯 等 | ~20 万 |
| 漱石 (既存) | (Phase 4b と同じ 7 作品) | 108 万 |
| **合計** | | **~380 万** |

### 実装

`scripts/download_aozora_meiji_taisho.sh` を追加 (既存 `download_aozora_soseki_works.sh` をテンプレートに):
- 各作品の Shift-JIS zip URL を列挙
- UTF-8 変換 + ルビ除去 + 編集注記除去
- 1 つの大きな `corpus/aozora_meiji_taisho.txt` に連結

### 注意点

- **仮名遣いの統一**: 旧字旧仮名作品 (鴎外初期や露伴) は文字種が爆発するため除外
- **文体の多様性**: 漱石・芥川・太宰で時代も文体も大きく違う → これ自体が **多様性を学ばせる学習信号**
- **vocab 拡大**: 3720 → 5000 chars 程度に増える見込み。 vocab_size 自動算出は既存実装で動く

### 期待値

- val_ppl: ~18.84 → **15.5〜17.0** (データ多様性で長尾分布の予測精度向上)
- 過学習開始の遅延: step 600 → step 1000+ に
- 生成文に各作家の文体的特徴 (太宰の独白調、 芥川の客観描写、 鴎外の歴史調) が混在する可能性

## Phase 5-4: モデル拡大 (d_model 384 → 512 / 768)

### 仮説

10.7M params は日本語の複雑さ (漢字 3700 + 活用 + 敬語) を捉えるには小さい。
GPT-2 small (124M params) ですら英語の流暢さに留まる規模なので、 まずは 20-50M を目指す。

### 段階的検証

| 段階 | d_model | n_layers | d_ff | params | 1 step 時間予測 (max_len=512) |
|------|---------|----------|------|--------|------------------------------|
| Phase 4b (現状) | 384 | 6 | 1536 | 10.7M | 7.7s (max_len=256) |
| 5-4a (中規模) | 512 | 6 | 2048 | ~20M | 12-15s |
| 5-4b (大規模) | 512 | 8 | 2048 | ~26M | 16-20s |
| 5-4c (最大) | 768 | 8 | 3072 | ~50M | 30-40s |

### 完走時間予測 (max_len=512 + Phase 5-3 コーパス、 end_step=1000)

| 段階 | 完走時間 |
|------|----------|
| 5-4a | 約 3.5 時間 |
| 5-4b | 約 5 時間 |
| 5-4c | 約 10 時間 |

### 期待値

- val_ppl: ~17 → **14-16 帯** (params 倍数 × 0.5-0.7 がだいたい改善幅の経験則)
- 生成文で **文脈の追跡、 敬語の整合性、 助詞の正確さ** が体感可能に改善
- 「ここまで来ても局所的に変なら、 本実装の理論的上限に近い」 と判断できる

### リスク

- M1 Max のメモリ (32GB-64GB) 上限への接近: 768 + max_len 512 + batch 32 で attention の memory が
  `seq² × n_heads × batch ≈ 512² × 6 × 32 × 4B = 200MB/layer × 8 = 1.6GB` 程度。
  Activation 含めても 10GB 以下なので問題なし。 もし出たら batch_size=16 に縮小
- 学習が不安定化する場合: lr_max を 1e-3 → 5e-4 に下げる (大モデルでは慣例)
- 過学習が再現: dropout 0.2 → 0.3、 weight_decay 0.1 → 0.15 で調整
